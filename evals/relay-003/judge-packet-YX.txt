=== ARM Y README.md ===
# 会议收尾板 · Meeting Wrap-Up Board

一个**双击就能打开**的离线小工具，用来给小组会议收尾：记要点、列行动项、导出备份。
不用装软件、不用联网、没有服务器、不需要任何依赖。

## 怎么用

1. 双击 `index.html`（用 Chrome / Edge / Firefox 都可以），整个工具就这一个文件。
2. **会议主题**：页首那一行，可空。
3. **会议记录**：左边的大文本框，想到什么写什么（窗口窄的时候会自动变成上下两栏）。
4. **行动项**：右半边。下面的输入框写一件回车一下，写清「谁、做什么、何时」，例如
   `张三 周三前把周报发到群里`。做完勾上，文字会划掉，右边有个 `×` 可以删。
   底部左边那句 `未完成 N 项 · 共 N 项` 就是收尾时要念的清单。
5. **导出备份**：页首右上角和页底各有一个「导出备份」（同一个按钮，看你在哪儿顺手），
   点了会下载一个 `meeting-YYYYMMDD-HHmm.json` 文件。里面是完整的会议内容
   （标题、记录、行动项及其勾选状态）。**文件里没有明文**（见下一节），
   打开看是一串乱码，发到群里被人扫一眼也看不出内容。
6. **从备份恢复**：点「从备份恢复」，选中之前导出的那个文件，内容就回来了
   （当前内容会先自动存进当天的副本，选错了也能找回）。
7. **清空**：页首最右边那个不显眼的「清空」，只在你真想重开一页时用（会先弹确认框）。

## 导出的文件里没有明文，但也不需要密码

- 备份文件打开后长这样：`MWB1:Iq1V4gBVIVgdUE7lX0ntri...`（一行 `MWB1:` 开头的乱码 + 校验码），
  会议主题、记录、人名都**看不到明文**。
- **不用记任何密码**：解码用的钥匙固定写在 `index.html` 里，你只要点「从备份恢复」选文件就行。
- 这是**「防止顺手被看见」的表层遮蔽，不是真正的加密**：拿到这个页面（或它的源码）的人
  是有办法解出来的。别用它保存真正需要保密的内容（比如密码、别人的隐私）。
- 以前的明文 `.json` 备份仍然可以「从备份恢复」导入，不会丢。
- 页面里自己的自动保存（浏览器本地存储）**仍然是明文**，那是你自己电脑上的草稿；
  只有「导出/发出去的那份文件」做了遮蔽。

## 写的东西不会丢

- 每次输入后约 0.25 秒自动保存，页首右上方会显示 `已保存 HH:MM:SS`。
- 关闭标签页、切换窗口、刷新前都会立即再存一次，最后几个字也不会丢。
- 数据存在**当前浏览器的本地存储**里（localStorage，键名 `mwb.draft.v1`），
  关掉浏览器、重启电脑都还在；换一台电脑或换一个浏览器不会自动带过去 —— 请用「导出备份」。
- 每天第一次保存时还会另存一份当天的副本（键名 `mwb.draft.v1.<年-月-日>.autosave`），
  即使误点「清空」，当天早些时候的内容仍留在这份副本里。
- 如果浏览器禁止本地存储（无痕模式、某些受管电脑），页首会出现红色提示
  `⚠ 浏览器阻止了自动保存，请点「导出备份」` —— 看到这句就请导出备份，别继续盲写。

## 注意事项 / 已知边界

- 「清空」会先弹确认框；它会清掉标题、记录和行动项。
- 导出的文件是备份，也是以后功能升级用的数据格式；页面提供「从备份恢复」按钮一键导回
  （`tests/core.test.js` 里有 round-trip 测试保证不丢字段）。
- 只有一个会议、一份草稿，不保留历史会议列表（要留存请每次导出备份）。
- **不看时间了**：早先版本有个页面上显示当前时间 + 会议计时（开始/暂停/归零）的功能，
  用不上，已整个撤掉（不是藏起来）。旧备份文件里的计时数据会被忽略，标题、记录、
  行动项照样完整导入。
- 不联网、无账号、无多人同步。行内文字写什么都可以（中文、emoji 都没问题）。

## 给开发者

```

src/core.js             # 纯逻辑（无 DOM、无存储），页面与测试共用同一份字节

tests/run.js            # 测试入口：node tests/run.js（零依赖，退出码 0 = 全绿）
```

- 改了 `src/core.js` 或模板后运行 `node tools/build-page.js`；测试会校验页面内嵌的
  core 与 `src/core.js` **逐字节一致**，不一致即失败。
- 运行测试：`node tests/run.js`。

# Export skin: no plaintext, no password

- Kind: system
- Status: decided

## Responsibility in the whole

Owns the newest requester feedback (verbatim):
"刚想起来一件事：导出的文件里别留明文，万一发到群里被人看见就尴尬了。但也别弄什么密码——没人记得住。你看着办。"

The two halves conflict literally: "no plaintext" is only achievable against someone holding
the file by making the content unreadable without a secret; "no password" means we may not ask
the user to hold a secret. This document records how the conflict is resolved so a later agent
does not have to guess: **the secret exists, but the user never sees or remembers it — it is a
constant compiled into `index.html`.** The exported file is therefore *unreadable at a glance*
(log-safe, group-chat-safe) and *trivially restorable* by anyone who has the page, which is the
only thing the requester actually asked for: avoid the awkward eyeball moment without adding a
step to their workflow. We call the mechanism a **skin (表层遮蔽)**, never "加密", in code,
UI copy and docs, because claiming encryption would be a lie (see "How this could look done yet
fail").

Threat model (who we defend against) — stated explicitly so nobody over-promises later:
- IN: a teammate skimming the file in a group chat / file list / email preview; a screenshot of
  the folder; someone opening it in Notepad and reading people's names and candid notes.
- OUT: a determined reader. The key sits in the page next to the export button, so anyone who
  reads `index.html` (or this repository) can decode the file. This is a *deterrent*, not
  confidentiality against a motivated party. If the requester ever needs real confidentiality,
  see "Alternatives considered" #1 — that is a different product decision and a new feedback.

## Applied capabilities

- `offline-file-protocol`: no network, no CDN, no `type="module"`, no dependency. The skin is
  implemented in `src/core.js` with hand-written base64, UTF-8 and PRNG code so it works on
  `file://` in every target browser *and* in plain Node for tests. No WebCrypto `SubtleCrypto`:
  it is unavailable on `file://` origins in some browsers and is async, which would open a
  window where the user could click again mid-export.
- `wrap-up-notes-ux`: export stays **one click** and must not grow a settings dialog, a
  passphrase prompt, or a "remember this key" moment. Restoring must be one click as well
  (`从备份恢复` → file picker) because "a backup you cannot restore is not a backup".
- `persistence-and-single-file.md`: the local autosave draft (`localStorage`) is NOT skinned —
  it is already the user's own machine and skimming it is not the reported risk. Only the
  artifact that leaves the machine (the download, and the copyable fallback text) is skinned.

## Alternatives considered

1. **Real encryption with a key derived from a user-chosen passphrase (PBKDF2/AES via WebCrypto).**
   Optimizes for genuine confidentiality against anyone without the passphrase. Costs: exactly
   the thing the requester vetoed ("没人记得住"), plus a prompt on every export, a lost-passphrase
   support conversation, an async API on a `file://` origin, and a v2 file format to migrate.
   Rejected — it contradicts the second half of the feedback and adds a step to a two-minute
   wrap-up. Kept as the documented escalation path if confidentiality ever becomes the ask.
2. **Random per-file key stored beside the file (e.g. `meeting-….json.key`).**
   Optimizes for a real secret the user never chooses. Costs: a second file that will be
   separated from the backup

# DESIGN — "会议收尾小工具" (Meeting Wrap-up Tool)

## 1. The brief (verbatim, vague)
> 给小组开完会收个尾做个小工具，就一个页面双击能开。写的东西别丢——刷新关掉都得在。最好能看着点时间。能顺手导出来个备份更好。

Decomposed into requirements:
| # | Requester's words | Requirement |
|---|-------------------|-------------|
| R1 | 一个页面双击能开 | One page, open by double-click, offline, zero external resources |
| R2 | 写的东西别丢，刷新关掉都得在 | Text you write survives refresh **and** closing the tab |
| R3 | 最好能看着点时间 | ~~A visible clock / elapsed timer~~ → **RETRACTED** (see §7) |
| R4 | 能顺手导出来个备份 | Easy export of a backup file |

## 2. Bounded assumptions (each with rationale)
The brief is vague, so every ambiguity below was resolved with ONE bounded
assumption. **Baton 2+ may not ask the requester — these are the contract.**

- **A1 — It is a meeting wrap-up noting tool, not a chat/todo app.**
  Rationale: "开完会收个尾" = wrap up after a meeting. The core artifact is free
  text you jot down *at the end* of a meeting (decisions, action items, notes).
  Assumption: a **single free-text editor** plus meeting metadata. Keeping it to
  one text area minimizes scope and matches "写的东西" (the stuff you write).
- **A2 — ~~"看着点时间" = a live wall clock AND a meeting elapsed timer.~~
  RETRACTED at Baton 3 by the requester ("之前那个看时间的功能先撤了吧，用不上。"),
  together with A2's whole state model and tests. See §7. Nothing replaced it.
- **A3 — Persistence = browser localStorage, single fixed key.**
  Rationale: a double-clickable `file://` page has no server. localStorage works
  on `file://` in Chrome/Edge/Firefox for the same path. Autosave on every
  keystroke (debounced) + on visibilitychange/beforeunload so **refresh and
  close both preserve the draft**. A single key `meetingwrap.v1` holding JSON.
- **A4 — Export = one click, one file, restorable on this page.**
  Rationale: "导出来个备份" = export a backup. Lossless + re-importable, works
  offline on `file://` (Blob + anchor). Since Baton 2/3 the content of that file
  is **skinned so it carries no plaintext** (see §6), extension `.mwb`; import
  ("从备份恢复") makes the round-trip meaningful. A human-readable `.md` export is
  offered as an explicit second click because a backup is sometimes meant to be
  read. **Import still accepts pre-skin plaintext `.json` backups.**
- **A5 — Meeting metadata = title + date, both auto-filled, editable.**
  Rationale: a backup with no title/date is useless later. Auto-filled so the
  user can ignore them and still get a sane backup.
- **A6 — No build step, no bundler, no network.** Single `index.html` with
  inline CSS/JS so double-click just works. Rationale: "双击能开".
- **A7 — Target browsers: modern Chrome/Edge/Firefox** (localStorage, Blob,
  URL.createObjectURL, crypto.randomUUID). Rationale: ordinary office machines;
  no IE support is a bounded, reasonable cut.

## 3. Architecture
- `index.html` — the whole UI (inline CSS + JS, zero external resources).
  The double-clickable artifact.
- `src/core.js` — pure, environment-agnostic logic (state model, autosave
  scheduling, export formatting, clock formatting). Written to be loaded by
  **both** the browser and Node tests. Exposes via a UMD-ish pattern:
  `window.MeetingCore` in browser, `module.exports` in Node.
- `tests/core.test.js` — Node built-in test runner (`node --test`), zero deps.
- `tests/smoke.js` — static checks on `index.html` (no external URLs, contains
  expected hooks) so we can prove "offline / zero external resources".

## 4. Data model (localStorage key `meetingwrap.v1`, format v2)
```json
{ "version": 2, "title": "string", "date": "YYYY-MM-DD", "notes": "string" }
```
- v1 (Baton 1) also had `startedAt` / `accumulatedMs` / `runningSince` for the
  elapsed timer. **The timer was retracted (§7)**, so v2 has none of them.
  `normalizeState`/`parseState` **ignore** those fields instead of rejecting the
  document, so a v1 draft or a pre-retraction backup still restores its notes.
  The stale fields are dropped on the next save/export (never carried forward).
- The key is still `meetingwrap.v1` on purpose: renaming it would orphan every
  existing draft (localStorage is the one thing that must not break).

## 5. Out of scope (deliberately)
Accounts, sync, multi-meeting library, rich text, encryption, server.

## 6. Feedback: "导出的文件里别留明文，但也别弄什么密码" — resolution

Verbatim (Baton 2): *"刚想起来一件事：导出的文件里别留明文，万一发到群里被人看见就尴尬了。
但也别弄什么密码——没人记得住。你看着办。"*

The two halves literally conflict: guaranteeing "no plaintext" against whoever
holds the file needs a secret; "no password" forbids asking the user to hold one.
**Resolution (kept by Baton 3, because we agree with it): the secret exists but
the user never sees it — it is a constant compiled into `src/core.js`, which sits
next to `index.html`.** We call it a **皮肤 / skin (表层遮蔽)**, never "加密" /
"encryption", in code, UI copy and docs — claiming encryption would be a lie.

Threat model, stated so nobody over-promises later:
- **IN (defended):** a teammate skimming the downloaded file in a group chat, mail
  attachment preview, file list or Notepad: they see base64, not names/notes.
- **OUT (not defended):** a determined reader. The constant ships with the page, so
  anyone who reads `index.html`/`src/core.js` can decode the file. It is a
  deterrent against the awkward moment, not confidentiality. If real
  confidentiality is ever asked for, that is a new decision (passphrase or a key
  file) — explicitly rejected for now because of "没人记得住".
- The **localStorage draft is not skinned**: it is already on the user's own
  machine, and skinning it would break the "old drafts still load" guarantee.

### What the sealed export is (Baton 3, final)
`sealBackup(plainJson)` → `MWSKIN1:` + base64(`{v, ct, d}`), a single-line ASCII
text file `meeting-<date>-<title>.mwb`:
- `ct` = plaintext UTF-8 XOR a SHA-256 counter-mode keystream keyed by
  `deriveSkinKey(SKIN_KEY, 'v1')` = 2000 chained SHA-256 rounds (hand-written
  SHA-256 / base64 / UTF-8 so it runs on `file://` and in Node with no WebCrypto,
  no dependency, no async
