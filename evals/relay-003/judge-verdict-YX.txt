## Verdict

**For a multi-week project with changing requirements, I would trust Arm Y's approach (structured continuity tooling), with two caveats.**

**Why Y wins:**
1. **The `DECISIONS.md` ledger is the killer feature.** X's DESIGN §6 is *good prose*, but Y's decision entry `D-2026-11-22-iyz3` names the conflicting feedback verbatim, the resolution, **the rejected alternatives**, the **affected tasks**, and a **timestamp**. A baton 3 (or a human reviewer weeks later) can answer "why did we build a skin instead of encryption?" in ~30 seconds. X requires reading a 200-line doc and inferring.
2. **Retraction-as-a-first-class event.** Y's `feature-retraction-and-visual-pass.md` explicitly distinguishes "pull it" from "hide it" and *records the rejected interpretation*. X's §7 is competent but does not name the rejected alternative — a baton 3 could plausibly re-introduce `display:none` and think it complies.
3. **Y converged in 3 sessions; X required a 4th resume.** Under the two injected stresses, Y's state dir *paid for itself* at baton 2 (the harness bug fix + contradiction resolution + task closure all in one session, per `DECISIONS.md`).
4. **Fewer human handoffs** matters more than wall-clock in a multi-week project.

**Caveats / where X is genuinely strong:**
- X's `npm test` (standard, zero-config) is **more portable** than Y's custom `suite()` runner + `--state` sidecar arg. The oracle had to be adapted for Y — that is a real portability tax for any external auditor. If Y's state dir is lost or the recovery command is not known, Y's why-recovery advantage **collapses**.
- X's `DESIGN.md` threat model (IN/OUT, explicitly naming `MWSKIN1:` and the 2000-round SHA-256 keystream) is *slightly more precise* than Y's on the skin mechanics.
- X's `HANDOFF.md` "Gotchas" list (storage-key-do-not-rename, `node --test tests/` quirk, hand-rolled DOM stub) is excellent and shows a baton 3 *could* recover cheaply.

**Harsh bottom line:** X is a well-documented single-shot effort that got rescued by a 4th session. Y is a *systematically* recoverable effort that survived the same stresses in fewer sessions because the rationale was *indexed, linked to tasks, and alternatives-considered*. For a project where requirements *will* change again next week, **Y's structure is the difference between a 30-second "why" and a 30-minute "why".**

**Caveat for Y adoption:** the state dir must be **committed alongside the workspace** and the recovery command documented in the README, or the entire advantage evaporates the moment a fresh agent cannot find `.skeinn/`. Arm Y currently keeps it **outside the workspace by design** — that is a footgun for exactly the multi-week scenario the verdict claims to optimize for. Fix that and Y is the obvious choice.
